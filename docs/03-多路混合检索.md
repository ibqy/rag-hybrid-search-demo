# 三、多路混合检索：从候选到 RRF

> 源码：[retrieval 包](../src/main/java/com/xb/rag/retrieval/)。离线对照见 [评测实验室](./07-RAG评估体系.md)。

## 两路互补，不是效果保证

关键词检索通常更适合型号、错误码和原文术语；向量检索通常更擅长语义改写。例如 `ERR_AUTH_401` 的定位与“登录后为什么立即失效”可能需要不同信号。但 BM25 依赖分词和字段映射，也不是严格的 ID 等值查询；向量检索并非一定找不到专有名词。

| 路由 | 本仓库入口 | 真实运行前提 |
|---|---|---|
| 向量 | `VectorRetriever` 调用 Spring AI `VectorStore` | 可用的 embedding 模型、兼容维度、已写入的向量及元数据 |
| BM25 | `Bm25Retriever` 调用 Elasticsearch | 正确索引名、字段映射、分析器及已写入文本 |
| 编排 | `HybridSearchService` 收集两路候选后融合 | 两路 `chunkId` 一致，候选顺序表达各自的相关性排名 |

`similarityThreshold` 是相似度门槛，不是元数据权限过滤。当前问答请求中的 `tenantId` 没有进入检索过滤，**不能依靠该字段实现租户隔离**。

## RRF：累加排名贡献

对去重标识为 `d` 的 chunk，定义：

```text
score(d) = Σ 1 / (c + rank_route(d))
           仅对包含 d 的路由求和

c = 60
rank_route = 该路由输入列表中第一次出现 d 的位置，从 1 开始
```

关键语义：

- **跨路求和，不是取最大值**。取 `max` 会丢失两路共同命中的贡献，不是这里的 RRF。
- 缺席某一路的贡献为 0；不填补虚构的末尾名次。
- 使用输入列表位置，而非结果对象中可能陈旧的 `rank` 字段；不使用原始向量分数或 BM25 分数。
- 同一路重复 `chunkId` 只让第一次出现贡献一次，不能重复投票；后续项仍按原始列表位置计名次。
- 按融合分数降序，同分按 `chunkId` 稳定排序，再截取最终 K。
- 融合结果应为新的结果对象并复制元数据，不能覆盖输入候选的分数、排名或元数据。保留输入才能做可信的单路对照。

### 手算示例：共同命中如何改变顺序

**以下是公式演示，不是实测结果，也不是消融 fixture 的报告。**

```text
Vector: [A, B, C]
BM25:   [B, D, A]
```

| chunk | Vector 名次 | BM25 名次 | RRF 分数（c=60） |
|---|---:|---:|---:|
| A | 1 | 3 | 1/61 + 1/63 ≈ 0.032266 |
| B | 2 | 1 | 1/62 + 1/61 ≈ 0.032522 |
| C | 3 | 缺席 | 1/63 ≈ 0.015873 |
| D | 缺席 | 2 | 1/62 ≈ 0.016129 |

结果是 `[B, A, D, C]`。如果同一路输入为 `[A, A, B]`，A 仅取第 1 位贡献，B 仍按第 3 位计分；两路各出现 A 一次则应相加。

共同出现只是“一致性”信号，不等于正确标签；两路也可能一起偏向同一噪声文档。不能由这个例子推出 RRF 在所有查询上更好。

## 三种 K 不要混用

```text
Vector 候选 Nv ─┐
                ├─ RRF 去重融合 → 输出 Kf → 排名评测 Ke
BM25 候选 Nb ───┘
```

| 参数 | 作用 | 实验时如何处理 |
|---|---|---|
| `retrieval.vector-top-k` | 向量候选深度，配置值 20 | 固定后再比较融合算法 |
| `retrieval.bm25-top-k` | 关键词候选深度，配置值 20 | 分层检查实体查询是否改善 |
| `retrieval.final-top-k` | 默认融合输出上限，配置值 8 | 评测需要 `Kf >= Ke`，否则报告短列表事实 |
| RRF 的 c | 平滑排名差异，本例为 60 | 不是返回条数，也不是相关性阈值 |
| 评测 K | 指标截断位置 | 所有对照采用相同 K |

若未来接入 Rerank，还应区分“送入重排的候选数”与“送入上下文的最终片段数”。当前问答控制器**没有调用 Rerank**，不要把 RRF 输出称为交叉编码器精排。

### 为什么不能把 0.45 用作 RRF 阈值

在两路、c=60、每路最多一次贡献的情况下，最大 RRF 分数是 `2/61 ≈ 0.032787`。把 Rerank 的 `0.45` 阈值直接用到 RRF，会过滤掉全部结果。RRF 分数既不是概率，也不能跨不同路数、候选深度直接解释为置信度。

## 排查顺序：先候选，再排名

1. **确认标签能在索引中定位**：两个索引中的 ID、版本、正文必须一致。`rag_docs` 等名称应与实际配置和导入目标一致。
2. **检查每一路原始列表**：相关 chunk 没有进入候选并集时，调整融合无法找回它；查分块、模型、分析器、过滤条件或候选预算。
3. **查看融合前后名次**：候选里有证据但最终 K 丢失，才是融合或截断问题。
4. **检查回归查询而非只看平均值**：实体型改善可能伴随语义型退化；记录逐查询差值。
5. **最后接入生成**：检索指标改善不自动意味着回答更忠实，答案评测需要另一套标签。

## 最小验证

在仓库根目录，Java 21 / Maven 3.9+：

```bash
mvn -Dtest=RrfFusionTest,EvalRunnerTest,RetrievalAblationTest test
```

重点查看：跨路累加、1-based 名次、单路重复、同分稳定性、输入不变、单路为空与两路皆空。冻结排名消融不访问真实索引；实验范围与报告解释见 [第 07 章](./07-RAG评估体系.md)。

官方参考：[Elasticsearch reciprocal rank fusion](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。它说明 RRF 的通用原理，不意味着本仓库调用了 Elasticsearch 原生 RRF API。

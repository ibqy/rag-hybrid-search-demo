# 六、向量库高阶运维 + 增量更新

## 问题背景

生产环境不是一次性导入所有文档就完了。文档频繁修改、新增、删除；向量数据量膨胀后查询变慢；多租户隔离需求出现。这些都需要向量库运维能力。

## 向量库配置

> 源文件：[`VectorStoreConfig.java`](../src/main/java/com/xb/rag/vectorstore/VectorStoreConfig.java)

支持两套选型：
- **pgvector**：中小体量，事务一致性强
- **Milvus**：百万/千万级向量，集群部署

### 索引选型与参数

| 索引类型 | 适用场景 | 召回率 | 构建速度 | 关键参数 |
|---------|---------|--------|---------|---------|
| HNSW | 高召回要求 | 高 | 慢 | M=16, ef_construction=200, ef_search=50 |
| IVFFlat | 海量快速构建 | 中 | 快 | nlist=100, nprobe=10 |
| IVF_SQ8 | 降低存储 | 中高 | 快 | 量化压缩，轻微精度损失 |

```java
public enum IndexType { HNSW, IVFFLAT, IVF_SQ8 }

// HNSW 参数权衡
private int hnswM;              // 连接数越大召回越高，内存越大
private int hnswEfConstruction; // 构建精度，越大召回越高
private int hnswEfSearch;       // 查询精度，越大召回越高但延迟增加
```

## 向量库管理服务

> 源文件：[`VectorStoreManager.java`](../src/main/java/com/xb/rag/vectorstore/VectorStoreManager.java)

运维操作统一入口：
- `initialize()` — 创建集合/表 + 建立索引
- `createPartition(name)` — 分区隔离租户数据
- `softDelete(chunkId)` — 软删除，后台异步物理清理
- `expireByTtl()` — 自动过期无用向量
- `rebuildIndex()` — 大数据量写入后重建索引

## 增量更新机制

> 源文件：[`IncrementalUpdater.java`](../src/main/java/com/xb/rag/vectorstore/IncrementalUpdater.java)

### MD5 变更检测

[`DocChangeWatcher.java`](../src/main/java/com/xb/rag/vectorstore/DocChangeWatcher.java)
```java
public boolean hasChanged(String currentMd5, String storedMd5) {
    if (storedMd5 == null) return true; // 新文档
    return !currentMd5.equals(storedMd5);
}
```

MD5 不变 → 直接跳过，不需要任何处理。

### 完整更新流程

```
用户上传文档 → 计算 MD5 → 对比库中历史 MD5
  ├─ MD5 相同 → 直接跳过（文档未变化）
  └─ MD5 不同 → 
      1. 删除该文档所有旧向量（软删除）
      2. 重新解析、切片、生成 embedding
      3. 写入新向量
      4. 更新元数据中的 MD5
```

```java
public void updateDocument(DocumentMeta meta, List<Chunk> newChunks, String newMd5) {
    // 步骤1: 删除旧向量
    for (Chunk chunk : newChunks) {
        storeManager.softDelete(chunk.getId());
    }
    // 步骤2: 写入新向量
    // 步骤3: 更新 MD5
    meta.setMd5(newMd5);
}
```

### 软删除机制

- 删除时只标记 `deleted=true`，不走物理删除
- 检索时过滤 `deleted=false`
- 后台定时任务批量物理清理 `asyncPurge()`

### 异步任务

大量文档解析/向量化是耗时操作（可能分钟级）：
```
HTTP 请求 → 生成 MD5 → 丢 Kafka 消息 → 返回"处理中"
Kafka 消费 → 解析 → 切片 → embedding → 写入向量库 → 完成
```

## 面试要点

- 为什么增量更新不做原地覆盖？向量是近似搜索，原地覆盖可能导致查询读到新旧混合结果。先删再写保证一致性
- 软删除为什么比物理删除好？删除操作是异步的，不阻塞用户请求；出错可恢复
- 增量更新失败怎么办？记录失败状态 + 重试队列；幂等设计保证重复执行不会产生重复向量
- 向量冷热分离是什么？向量库只存向量和元数据指针，原始文件放 OSS，降低向量库存储成本
